# Attempt Graph contract

## Closed vocabularies

The Harness attempt graph is carried by the `coach_problems` and `coach_nodes`
tables of the Teacher store. Its vocabularies are the `COACH_*` constants in
`teacher/scripts/th/constants.py` and the node roles and statuses written by
`teacher/scripts/th/coach.py`.

Practice states:

`HARD_LOCK`, `SEALED`

Admission statuses:

`READY`, `NOT_CS_AI`, `NEEDS_CLARIFICATION`, `INCORRECT_AS_STATED`, `UNVERIFIED`

Epistemic codes:

`NONE`, `KNOWN_OPEN`, `TRUTH_UNVERIFIED`

Node origins:

`learner`, `coach`

Learner node roles, one per submitted step:

`local_step`, `exploratory_idea`, `conclusion`

Coach node roles:

`obstacle`, `hint`, `incubation`

This is the storage vocabulary, not an actor allowlist. In `HARD_LOCK`, the
Coach creates only the three Coach roles, and it creates an `obstacle` only
deterministically, when a step is judged `invalid`. No model output names a
node role, status, or ID.

Node statuses:

- learner nodes: `verified` (decision `valid_so_far`), `refuted` (decision
  `invalid`), or `unresolved` (decision `needs_justification` or `unclear`); a
  `not_applicable` decision stores no node;
- `obstacle`: `open` or `resolved`;
- `hint` and `incubation`: `shown`.

Completion statuses:

`NOT_COMPLETE`, `ROUTE_READY`, `VERIFIED_SOLVED`

A learner node stores its text, role, decision, status, first-error code, and
attempt flag, which is true only for `valid_so_far`, `invalid`, and
`needs_justification`. A `conclusion` is a learner node with role
`conclusion`; changing wording cannot turn a `local_step` into a conclusion or
back. An `obstacle` stores the first-error code of the step it blocks and,
once resolved, the resolving node and its ordinal. A `hint` stores the
accepted hint text. An `incubation` marker stores no text.

An exploratory idea is a learner node with role `exploratory_idea` that
records the learner step number it connects to, or `0` for the problem; it
carries no idea type or connection reason. Research incubation is a
projection, not a graph change: it may reference only one or two learner nodes
by step number, and it adds only an empty `incubation` marker. A provisional
conditional hypothesis enters the graph only if the learner confirms it,
supplies their own basis, and resubmits it as a step.

## Links

Three links connect nodes:

- `connects`: on an exploratory idea, the learner step number it connects to,
  or `0` for the problem, named by the learner;
- `blocks`: on an obstacle, the learner node judged `invalid` that created it;
- `resolved_by` with `resolved_at`: on a resolved obstacle, the later learner
  node, judged `valid_so_far` with `resolves_obstacle=true` by both the Coach
  and the Guard, that resolved it, and that node's ordinal.

There are no other edges, no branches, no merges, and no dependency edges to a
problem node. The Harness keeps no dependency chain between steps: the
completion gate reads roles, statuses, and ordinals, not a closure. Strict
completion uses ordinals to require that a verified conclusion comes after
every obstacle, every resolution, and a verified `local_step`.

Ordinary chat may still track forks, pauses, and merges as route handling
(`ACTIVE`, `PAUSED`, `DEPRIORITIZED`, `MERGED`) and the technical route
statuses `UNKNOWN`, `VALID_SO_FAR`, `NEEDS_REPAIR`, `ROUTE_READY`,
`VERIFIED_SOLVED`, or `PROVABLY_BLOCKED`. `PROVABLY_BLOCKED` requires a scoped
obstruction that rules out every continuation within that scope; a refuted
step never supplies that conclusion by itself.

## History

Every practice write is one compare-and-swap transaction on the Teacher
store's execution head; the resulting revision is the recovery head of the
attempt graph. Each commit appends an `execution_advanced` event naming its
action. Node IDs are generated by the Harness and never taken from model text.

Learner nodes are never edited after they are written. An obstacle's row is
rewritten when it is resolved; it keeps its ID and ordinal and gains
`resolved_by` and `resolved_at`. The event log records that a step was
committed, not the previous row, so the resolution is reconstructible from
those fields and the ordinals rather than from a stored diff.

The learner cannot edit, remove, or resolve an obstacle: there is no learner
graph action. Only a later step, not an exploratory idea, that the Coach
judges `valid_so_far` and that both the Coach and the Guard mark
`resolves_obstacle=true` resolves the earliest open obstacle.

The problem row also changes in place: the off-topic counter, the ordinal of
the last route-summary offer, and the sealed state with its completion status,
exit mark, or superseded time. A completion check stores nothing unless it
passes; a passing check rewrites the problem row as `SEALED` with the
completion status. There are no stored assessments or snapshot hashes.

## Write validation

Before a transaction, the Harness has already:

1. accepted the Coach review and Guard verdict only with their exact closed key
   sets, type-checked closed values, and vocabularies;
2. verified that any quote is a substring of the current learner text;
3. derived the node status and attempt flag from the decision, the obstacle
   from `invalid`, and a resolution from agreeing `resolves_obstacle` values by
   fixed code, not from model text;
4. generated every node ID and ordinal itself;
5. for incubation, required the selected IDs to be among the anchors it chose
   from the learner's own nodes.

The problem row and all nodes of one step commit in one SQLite transaction and
roll back together on any failure.

## Context selection

Build a new bounded packet for every model call:

- step review: the exact problem, the last 12 learner nodes (ordinal, role,
  status, and text), the first open obstacle's category or null, the current
  step and role, for an exploratory idea the connected step's text (at most 600
  characters) or the marker `problem`, the closed decision and first-error
  vocabularies, and a fixed instruction;
- Guard: the same packet and the Coach's closed fields;
- admission: the exact problem, the closed admission and epistemic
  vocabularies, and a fixed instruction; the auditor also receives the
  reviewer's closed fields;
- hint: the exact problem, the first open obstacle's category, the last eight
  learner nodes, every earlier hint, and the 120-character limit;
- incubation: the kind, the one or two chosen learner nodes (ID and at most 600
  characters of text), and the allowed question codes;
- lenient completion: the exact problem and the learner route (role, status,
  and text of every learner node).

No packet contains the event history, Teacher answer-path material, or any
earlier model output other than stored hints. The bundled backend adapter
truncates a serialized packet above 60,000 characters.

An `obstacle` is an open obligation until it is `resolved`. Completion,
hint eligibility, and the route summary use the stored statuses directly.

## Local route-summary projection

The local summary reads every learner node of the latest submitted problem in
ordinal order, plus the first open obstacle. It does not mutate anything.

Only recorded learner text may be quoted, at most 120 characters per step.
Learner statuses render as `成立` (`verified`), `不成立` (`refuted`), or
`未定` (`unresolved`). The first open obstacle renders as its first-error
category. The renderer may not infer a new derivation, a use of an unused
condition, a route status, or a `PROVABLY_BLOCKED` judgment.
